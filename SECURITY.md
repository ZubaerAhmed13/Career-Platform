# Security model and launch blockers

Supabase Auth manages credentials and session tokens; @supabase/ssr manages cookies, and protected pages call auth.getUser() server-side. Server-side profile update uses verified user.id rather than user input; Postgres RLS independently enforces ownership. The database intentionally has no client document-upload policy. An optional server-only service-role key is required for trusted AI persistence and self-service full-account deletion; never expose it to the browser.

**Limitations requiring verification before launch:** live registration/password recovery email delivery, rate-limit/abuse protections, staging cross-account RLS and upload tests, full CSRF/origin review, CSP configuration, third-party dependency auditing, logging/monitoring, data export/deletion, GDPR notices, retention and DPA/legal review, optional German generated-document quality review, scanning and private-download flow. Do not claim GDPR compliance on current implementation. Public NEXT_PUBLIC_ variables are not secrets, but server service-role credentials must never use that prefix.

## Milestone 2 threat model and limitations
Career tables implement RLS and same-owner composite FK constraints. Private JSON export checks the authenticated account and filters every table by verified user ID; responses disable caching and exclude authentication secrets. A user must explicitly confirm deletion. The AI key remains server-only and absent keys disable interviews. AI input is limited and context is scoped to a small number of approved records. Proposals require schema validation, user-evidence quotes and explicit acceptance, with SQL-transactional approval. Direct PDF/DOCX or personal-file uploads stay disabled until scanning and storage policies are reviewed.

**Staging verification required:** migrations applied to the correct project, two-account cross-ownership tests (including malicious linked IDs and AI sessions), CSRF/origin and concurrency review, permission/function audits, operational abuse/rate limits, consent & provider privacy/legal assessment, production identity email delivery, file retention/export/deletion and privacy rights. Passing CI does not establish GDPR compliance or live security.

## Fail-closed document import
Server actions reject files without `CLAMAV_HOST`, require explicit consent, cap binary size to 2 MB and validate extensions against file signatures. A real clamd INSTREAM request must return a clean verdict *before* parsing with `unpdf` or `mammoth`. PDF page counts and DOCX archive declared expanded-size/entry counts are bounded. The file itself is never persisted. Extracted text becomes an **unreviewed** suggestion, never a confirmed fact. No public storage write policy has been granted.

Operational gaps: ClamAV deployment/version/signature updates, private network isolation, malware test fixtures, memory/CPU sandboxing of parsers, decompresser fuzz tests and integration tests are **not yet verified**; do not expose this upload route publicly without those safeguards. Quota migration 006 caps model requests but not anonymous signup abuse or all API endpoints. Public deployment still requires a defense-in-depth security review.

## Verified AI provenance (migrations 007–008)
The earlier owner-only RLS policy permitted users to insert any `career_interview_messages.role`, including `assistant`. New migration 007 removes that path. An authenticated user may insert only their own `user` messages; only a protected service-role function writes genuine assistant replies and suggested facts with matching direct user evidence. Migration 008 applies the same service-only pattern to AI extraction from pasted CV text and introduces a NOT VALID HTTP(S) evidence-URL constraint for subsequent writes. Existing unsafe URL records must be audited/cleaned before validating the constraint; the UI independently refuses dangerous schemes.

The protected server must set `SUPABASE_SERVICE_ROLE_KEY`. It is **highly privileged**: it bypasses RLS, must never be prefixed `NEXT_PUBLIC_`, committed, exposed in network responses or used directly by a Client Component. The server authenticates the user via Supabase `getUser()` first and restricts the privileged RPC to that user and an active session. Functions require a `service_role` JWT claim and are explicitly revoked for `anon`/`authenticated`. Unit and CI checks cannot prove these policies in the live project; run the staging authorization suite before release.

## Provenance and checked SQL runtime (migrations 009–010)
Normal client users are limited to manually authored confirmed new records. Record updates may change career content but cannot change user ID, record ID, creation time, source or review status. Database revision triggers and owner policies enforce this independently of the UI. AI-origin proposals and status changes continue to use reviewed, owner-scoped database functions.

The new PostgreSQL CI job **actually executes SQL**, rather than only checking file existence; it uncovered and allowed repair of a runtime ambiguity in verified AI persistence. Supabase-managed auth/storage objects are replaced with test fixtures in this job, so hosting, Supabase Auth JWT enforcement, privileged key handling and real RLS acceptance remain separate live checks.

## Account export and permanent deletion (Step 2 continuation)

The Settings page now provides an owner-scoped profile + Career Vault JSON archive, distinct from Vault-only export. Account deletion requires the verified signed-in identity, exact user confirmation, password reauthentication from an isolated unprivileged client, an available server-only admin key and a private Storage preflight. Only then can the Auth Admin hard-delete call occur; database rows cascade through existing foreign keys. OAuth-only identities, owner-held Storage objects, backup retention, regulatory controller notices and live staging acceptance remain operator-controlled release gates. See `docs/DATA_RETENTION_AND_ACCOUNT_ERASURE.md`. Do not claim that an archive contains every data category or a hard delete purges backups.

## October 13, 2026 — read-only hosted security audit

On the connected CareerOS Supabase project, migration history shows **18 applied migrations** and the schema catalog confirms **RLS enabled on all 11 exposed public tables**. `career_ai_usage` intentionally exposes zero normal-client policies; quota is operated through owner-scoped RPCs.

For all **nine** authenticated `SECURITY DEFINER` RPCs reported by the Supabase security advisor, read-only catalog checks confirm: `anon` lacks `EXECUTE`, `authenticated` has `EXECUTE` by design, the function has an empty/restricted search path, and its code references `auth.uid()` and user ownership columns. These are **structural audit results, not proof that every complex RPC branch is exploit-free**. Two-user authenticated hostile-input and concurrency tests remain required before release. Do not revoke all nine user-facing RPC permissions merely to silence the linter; apply fixes only after a scope-by-scope review.

**Security configuration remains incomplete:** [Supabase leaked-password protection](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection) is disabled and requires authorized operator configuration. CSP, realistic provider rate-limit and CSRF evaluation, automated dependency security checks, backup expiry and controller privacy disclosure are not yet signed off. No prod account or data was modified during these checks.
